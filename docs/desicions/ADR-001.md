# Model Approval Chains as an Ordered Sequence of Steps
## Status

Accepted
## Context

The [[product-spec]] requires that some request types be routed directly to a fulfillment queue, while others require approval first, and approval itself can be either a single approver or a sequential multi-step chain (e.g. "manager → dept head"). While drafting the Routing & Approval's data flow, we needed to decide how to represent "who needs to approve this, and in what order" in a way that supports both cases without treating them as fundamentally different mechanisms.
## Decision

Approval chains are modeled as an ordered sequence of approval steps, not a single `approver` field on the request. A request type with approval-required routing has an `ApprovalChainTemplate` made up of one or more ordered `ApprovalStepTemplate`s (e.g. step 1 = requester's manager, step 2 = requester's dept head). At runtime, each request that goes through approval gets its own `ApprovalStepInstance` records, one per step, decided in order.
A single-approver chain is simply a sequence of length one. It uses the same structure, not a separate code path.
## Alternatives Considered

- **Single `approver` field on the request, re-assigned as the chain progresses.** Rejected: this would require overwriting or discarding the previous approver's decision to move to the next one, destroying step-by-step history and making "who approved this and when" (an audit requirement) harder to reconstruct. It also forces a separate mechanism for single-approver vs. multi-step chains, since a plain field can't represent "then also needs dept head" without extra flags.
- **Two separate models; one for single-approval requests, one for multi-step chains.** Rejected: this doubles the logic for routing, escalation, and audit history, for no real benefit, since a single approver is just a chain of one and doesn't need special-casing.
## Consequences

- **Positive:** approval history is naturally preserved (each step is its own durable record, not overwritten); multi-step and single-step approval share one implementation path; adding a new step to a chain later (e.g. requiring dept head approval for a request type that previously only needed manager approval) is a configuration change, not a structural one.
- **Negative:** slightly more upfront complexity than a single field; even the simplest single-approver case goes through the same sequence machinery.
- **Follow-on decision this enables:** because each step is its own record, later work established that a request's chain must be snapshotted from the template at creation time (see [[data-model]], Storage section) so that a routing-rule change doesn't retroactively affect a request already mid-approval. That snapshotting only makes sense because the chain is structured as discrete step records in the first place.
