# Context

While drafting the architecture and data flow of the routing / approval system, certain decisions had to be made concerning hierarchy chains and specific requests rules.
# Decisions

- Routing rules are per request type, not per department. A department can have some direct-routed types and some approval-required types side by side. This matches the spec's requirement directly and avoids forcing every request in a department through the same path.
- Approval chains are modeled as an ordered sequence of steps, not a single "approver" field. This is required to support "manager → dept head" sequential approval as stated in the requirement, and generalizes to single-approver chains as a sequence of length one, avoiding two separate code paths.
- Manual reassignment is treated as an override after routing, not a replacement for automated routing. Automated routing should handle the common case; admins step in only for exceptions.
